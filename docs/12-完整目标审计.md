## VM 类型与方法

`resources/vm/4.4.0/type-system.json` 记录每个 IR 类型对应的 SOL 名称、DynamicIO 名称、C# 属性类型和端口 Getter/Setter。

VM 4.4 的脚本端口定义没有原生 bool，确定性生成器统一用 VM int 端口承载，`false/true` 编码为 `0/1`，并在 C#/Python 表达式边界自动转换。显式自定义源码若声明 bool 端口会被阻断并要求改用 int，避免生成无法由 VM 属性生成器支持的端口。

反编译的 `GenerateUserPropertyCs` 在 C# 输入列表为空时不会生成任何 partial 属性，导致仅输出脚本在 VM 中缺少输出属性。Compiler 会为这种模块加入不可见、不可订阅的内部 int 输入锚点；它不进入 Requirement、用户端口清单或默认值关系，只用于触发 VM 属性生成。M10 回归验证该锚点在 Input 中存在、在 DynamicIO 中隐藏，并验证输出脚本仍能离线编译。

`resources/vm/4.4.0/api-catalog.json` 进一步记录变量模块方法。变量模块的 int、float、string 即使在 IR 中是标量，VM API 仍以数组读写；生成器读取首元素并提供类型默认值，写入时包装单元素数组。单个 ROIBOX 同样执行首元素/单元素数组转换。image、byte、pointset 和所有几何类型调用各自的 `GetVar…/SetVar…`。

M8 回归检查 30 个不同的类型化 Getter/Setter 方法，并让 18 个 VM 4.4 可选原生类型同时经过 C# Input 与 Output 写入、脚本属性类型和离线编译；bool 另按 int 0/1 兼容路径验证。Circle 保留变量 Getter/Setter，但因 VM UI 无对应端口选项而由编译器阻断。

## 已确定的结构化操作

- ShellModule：强类型输入输出、模块获取、标量/数组/参数读取、参数设置、全局/局部变量、pointset 转换、日志、等待。
- PyShellModule：已确认 bool/int/float/string 及对应数组的端口表达式、全局/局部变量、日志、等待和默认值回退。项目内没有 Python IoHelper 访问 image/ROI/几何/pointset 的真实样本，这些端口返回 `PYTHON_COMPLEX_TYPE_UNCONFIRMED`；相同复杂类型在 C# ShellModule 已完整支持。
- GlobalScript：单次/连续/停止流程、连续间隔、流程 int/float/string 输入、启动全局通信、发送通信数据、方案另存/加载、全局变量、日志、等待。
- 表达式：input、result、literal、binary、unary、index；支持算术、比较、逻辑和结构化 operation condition。

确定性操作的错误策略目前只接受实际生效的 `onError=fail`（或省略）。`continue` 与 `set-output-failed` 不会被静默降级，而是返回 `ON_ERROR_POLICY_UNSUPPORTED`；需要逐操作恢复语义时必须使用完整自定义源码。

项目内经典 SOL 中无法归纳为通用安全操作的算法（DXF、HSL、共享内存、VisionDesigner 工具等）保留为完整 `source`，由 AI 放入 IR 后仍接受载体契约、依赖门禁和离线预编译；AI 不接触 SOL 二进制。显式 `source` 与结构化 `operations` 不得同时出现，避免操作被静默忽略。

## 依赖与执行阶段

- `shell-reference-catalog.json` 从经典 HSL/DXF SOL 记录 `ShellRefrences` 的真实编码：系统程序集类型 0、`Script.Methods.dll` 类型 3、用户程序集类型 4、VM 程序集类型 6。
- 目录内已验证引用按 `system`、`vm-sdk`、`operator-sdk`、`third-party` 角色及证据类型使用；目录外自定义 DLL 只有在 Requirement 同时声明 `path` 和用户程序集类型 `referenceType: 4` 时才可进入构建。Core 会校验程序集 Identity、CLR metadata、目标框架、版本、x64/AnyCPU、外部文件递归依赖和 SHA-256，输出依赖清单与显式部署包，不自动写入 VM 安装目录。VM SDK 只能使用安装目录中的运行时文件，不能以部署包覆盖。
- 目录中带项目内 SOL 证据的程序集使用已验证类型；未知名称只有在用户提供真实 DLL 路径并明确声明用户程序集类型 4 时才允许写入，否则返回 `REFERENCE_TYPE_UNCONFIRMED`。写入后 parser 必须读回引用，且 C# 离线预编译必须成功。
- Python 声明的包由 VM 自带 Python 使用 `importlib.util.find_spec` 实际探测；缺失返回 `PYTHON_DEPENDENCY_MISSING`。
- 确定性 C#/Global `execution.mode=init` 会把操作生成到 `Init()`；载体特有 callback 必须提供完整 source，避免伪造回调参数语义。

## Desktop 用户操作层

默认界面只暴露自然语言、创建/补丁模式、Patch 基底选择和一个“生成 SOL”按钮。Requirement、输出目录、独立校验与诊断均折叠为高级选项；成功后提供复制路径和打开所在文件夹。MCP/CLI 保留完整专业接口，但不把这些复杂度推给普通 Desktop 用户。

Create 支持按 IR 创建多个流程，并把脚本模块放入各自声明的流程；模块默认不连接。VM 执行连接只在顶层 `connections` 明确声明时建立，且禁止跨流程连接。

## Patch 安全

- 输入 SOL 永不原地覆盖并验证 SHA-256 不变。
- 目标模块必须在基底或本次生成模块中存在。
- 参数必须来自解析到的算法参数、DynamicIO/生成端口，或 `module-parameter-catalog.json` 中带项目内证据的动作参数。
- `N点标定1.Clear` 来自经典 `基础.sol` 源码证据；伪造参数返回 `MODULE_PARAMETER_NOT_FOUND`。
- 项目内修改器对 ModuleFrame v4 错用 v7 名称槽；Core 在写回后按 v4 的 UTF-16LE/256 字节槽重建。经典 `基础.sol` Patch 前后警告集合一致，业务模块全部保留。

## 运行边界

离线 C# 编译、Python 语法、parser 与 inspect 本身不能证明 VM 调度和 DynamicIO 实际值，因此 Codex 未打开 VisionMaster。2026-07-15 用户已确认最终候选的三类脚本正常、四个默认值在 UI 可见，并且保存、关闭、重新打开后仍正常；manifest 已据此更新为 `runtimeValidated=true`。通信设备和第三方 SDK 的具体业务效果仍只对声明并实际部署的对应环境负责。

## 发布与产品完整性

`scripts/publish.ps1` 对 Core、CLI、Domain Worker、Pi Agent、MCP、Desktop 执行 Release 构建和回归，再生成 CLI、Desktop、MCP 三个 win-x64 产品目录。Desktop 内置固定 Node、Pi Agent 和自包含 Worker；发布检查要求 `.sol` 数量为 0，并生成 `dist/release-manifest.json` 记录关键组件哈希。
