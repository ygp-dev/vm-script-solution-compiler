# VM Script Solution Compiler：VM 4.4 技术参考

本文是编译器项目的 VM 4.4 权威技术参考。构建时不要再次读取原始 PDF、旧 skill、VM SDK Samples 或网络；原始材料仅作为本文的编制来源。

## 1. 环境与版本

启动后首先执行 `scripts/detect_vm_install.ps1`。检测优先级：

1. `VISIONMASTER_HOME`
2. `VM_HOME`
3. `MVDALGO_DEV_ENV`：值通常指向 `<VM根目录>\MVDAlgorithmSDK`，取父目录
4. `PATH` 中包含 `VisionMaster<版本>` 的目录，向上归一化到 VM 根目录

当前已验证环境：

```text
MVDALGO_DEV_ENV=C:\Program Files\VisionMaster4.4.0\MVDAlgorithmSDK
VM_ROOT=C:\Program Files\VisionMaster4.4.0
```

VM 根目录至少应包含 `Development`、`MVDAlgorithmSDK` 和 `Applications`。检测失败时停止生成，要求用户设置 `VISIONMASTER_HOME`；不要硬编码安装路径，不要扫描整个磁盘，不要在运行时查询网络。

全局脚本官方资源目录由环境检测结果拼接得到：

```text
<VM_ROOT>\Applications\GlobalScript
```

检测脚本在 JSON 中输出 `globalScript` 和 `globalScriptAvailable`。该目录包含全局脚本编辑器、默认源码工程、引用 DLL 与官方示例。项目已将生成所需的默认模板和中文 4.x 示例复制到 `resources/vm/4.4.0/global-script/`，因此运行时无需重复读取安装目录；只需用 `globalScriptAvailable` 判断当前安装是否具备全局脚本组件。

## 2. 三类脚本

| 类型 | SOL 载体 | 用途 | 输入输出 |
|---|---|---|---|
| 全局脚本 | `SolutionFile\GlobalScript_0` | 方案初始化、流程控制、回调、跨模块操作 | 全局变量或 VM SDK |
| C# 用户脚本 | `ShellModule`，脚本位于 ModuleFrame 的 `ShellContent` | 流程内按执行链运行的用户逻辑 | 模块 DynamicIO、订阅 |
| Python 用户脚本 | `PyShellModule`，脚本位于 ModuleFrame 的 `ShellContent` | 流程内 Python 逻辑与第三方库 | 模块 DynamicIO、订阅 |

全局脚本不是流程模块；ShellModule/PyShellModule 必须属于 Procedure，并同时具有 VmServer.xml 模块记录、ModuleFrame、UiParamData 和流程归属。模块默认可以互不连接，只有 Requirement 明确提供 `connections` 时才写执行连线。

### 2.1 全局脚本契约

`GlobalScript_0` 是以 NUL 结尾的 UTF-8 JSON：

```json
{
  "Version": "V3.4.0",
  "ScriptPassword": "",
  "ScriptContent": "...",
  "ScriptRefences": []
}
```

字段拼写 `ScriptRefences` 和元素字段 `refrencesType` 是 VM 原始拼写，不要修正。默认 C# 入口：

```csharp
public class UserGlobalScript : UserGlobalMethods, IScriptMethods
{
    public int Init() { return InitSDK(); }
    public int Process() { return DefaultExecuteProcess(); }
}
```

可按需求覆写 `ResultDataCallBack(IntPtr outputPlatformInfo, IntPtr puser)`。保留类名、基类、接口及 `Init`/`Process` 的 `int` 返回值，除非同版本成功 SOL 提供其他契约。

官方工程 `GlobalUserScript.csproj` 已确认：

```text
TargetFrameworkVersion = v4.6.1
Debug/Release x64: PlatformTarget = x64
默认输出类型 = Library
```

官方基础引用：`mscorlib`、`System`、`System.Core`、`System.Drawing`、`System.Windows.Forms`、`VM.GlobalScript.Methods.dll`、`iMVS-6000PlatformSDKCS.dll`、`Apps.Json.dll`。按模块操作需要增补 `VM.Core`、`VM.PlatformSDKCS` 以及对应模块的 `*Cs.dll`。只引用脚本实际使用的程序集。

官方 VM 4.x 示例已内置于 `resources/vm/4.4.0/global-script/samples-ch-4x/`，可直接作为代码模式来源：

| 示例 | 已证实用法 |
|---|---|
| `全局脚本_模块参数配置.cs` | `VmSolution.Instance["流程.模块"]`、`VmProcedure.Run()`、模块 `ModuParams/ModuResult`、局部变量读写 |
| `全局脚本_模块输入参数.cs` | `ProcedureParam.SetInputImage_V2`、`SetInputInt`、`SetInputFloat`、`SetInputString` |
| `全局脚本_通信接收.cs` | `StartGlobalCommunicate`、`RegesiterReceiveCommunicateDataEvent`、接收事件、`VmSolution.Save/Load` |

### 2.2 官方 VM 4.x API 模式

取得流程与模块：

```csharp
VmProcedure procedure = (VmProcedure)VmSolution.Instance["流程1"];
IMVSFastFeatureMatchModuTool tool =
    (IMVSFastFeatureMatchModuTool)VmSolution.Instance["流程1.快速匹配1"];
```

设置模块参数并读取结果：

```csharp
FastFeatureMatchParam param = tool.ModuParams;
param.MaxMatchNum = 10;
procedure.Run();
FastFeatureMatchResult result = tool.ModuResult;
```

读写流程局部变量：

```csharp
procedure.LocalVariable.SetVarInt("var0", new int[] { 1, 2 });
int[] values = procedure.LocalVariable.GetVarInt("var0").pIntVal;
```

设置流程输入：

```csharp
ProcedureParam input = procedure.ModuParams;
input.SetInputInt("intX", new int[] { 10 });
input.SetInputFloat("floatY", new float[] { 2.345f });
input.SetInputString("stringZ", new InputStringData[] {
    new InputStringData { strValue = "abc" }
});
```

图像输入使用 `SetInputImage_V2(name, new ImageBaseData(bitmap))`，并在流程运行后释放 `Bitmap`。所有 `VmSolution.Instance[...]` 结果都先判空；模块专用类型必须引用对应 `*Cs.dll`。

通信回调初始化：

```csharp
int ret = InitSDK();
StartGlobalCommunicate();
RegesiterReceiveCommunicateDataEvent();
return ret;
```

覆写 `UserGlobalMethods_OnReceiveCommunicateDataEvent(ReceiveDataInfo dataInfo)`，检查 `dataInfo`、`DeviceData` 与 `DeviceID`。保存/加载等可能阻塞的操作可使用 `Task.Run`，但避免并发重入。

### 2.3 用户脚本模块契约

已由 VM 4.4 开发样本确认模块类型名为 `ShellModule`、`PyShellModule`。样本已解包为 `resources/vm/4.4.0/script-base/`，正式项目不保存 `.sol` 模板。两类模块模板已内置完整 RawFrameData，可直接修改：

- `ShellContent`
- `DynamicInData`
- `DynamicOutData`
- 显示名、模块 ID、GUID、UiParamData
- 执行连线与输入订阅

ShellModule 的二进制参数顺序为 `Version`、`Input`、`Output`、`ShellContent`、`AssemblyGuid`、`DynamicInData`、`DynamicOutData`，样本版本为 `V3.2.0`。默认入口为：

```csharp
public partial class UserScript : ScriptMethods, IProcessMethods
{
    public void Init() { }
    public bool Process() { return true; }
}
```

PyShellModule 的二进制参数顺序为 `DynamicInData`、`DynamicOutData`、`ShellContent`、`Input`、`Output`。默认入口为：

```python
def Process(data) -> int:
    moduleVar = IoHelper(data, INIT_MODULE_VAR)
    globalVar = IoHelper(data, INIT_GLOBAL_VAR)
    localVar = IoHelper(data, INIT_LOCAL_VAR)
    return 0
```

Python 模块输入只读，通过 `moduleVar.<name>` 取得；输出只写，通过 `moduleVar.<name> = value` 设置。全局/局部变量使用 `GetValue(name)` 与 `SetValue(name, value)`。变量必须严格匹配定义类型，转换要显式执行，缩进使用 4 个空格。默认模板分别位于 `resources/vm/4.4.0/script-templates/shell-module.cs` 与 `py-shell-module.py`。

## 3. 提示词到输入输出

先整理为以下契约，再写脚本：

```json
{
  "vmVersion": "4.4.0",
  "carrier": "global|csharp-module|python-module",
  "scriptName": "脚本1",
  "procedureName": "流程1",
  "execution": "init|once|continuous|callback",
  "inputs": [
    {"name":"A","type":"float","default":0,"required":true,"description":"输入A"}
  ],
  "outputs": [
    {"name":"Result","type":"float","description":"计算结果"}
  ],
  "dependencies": []
}
```

区分配置参数与运行时端口。模块运行时端口写入 `DynamicInData`/`DynamicOutData`；订阅使用 VmServer.xml `Subscribe` 关系。动态端口在订阅关系中通常以 `%参数名%` 表示。类型必须前后一致，例如 `int→int`、`float→float`、`image→image`。

生成前检查：名称唯一、类型受 VM 4.4 支持、默认值可序列化、输出在所有正常分支赋值、错误分支有状态/返回码。

## 4. CurrentProcess 与模块操作

已知写法：

```csharp
CurrentProcess.GetModule("N点标1").SetValue("Clear", "");
```

用途是按模块显示名取得当前流程模块并写入参数，例如清空标定点。生成类似调用必须：

1. 从待生成 SOL 的模块表确认显示名存在且唯一。
2. 从模块参数定义确认 `Clear` 可写，并确认值类型；空字符串不能自动推广到其他参数。
3. 确认调用发生在包含该模块的流程上下文中。
4. 包装异常或检查返回结果，避免模块缺失导致脚本中断。
5. 在构建报告记录模块名、参数、值和调用时机。

不要凭中文功能名称发明参数。例如“清空标定点”只有在目标模块确实公开 `Clear` 时才能生成上述代码。

## 5. C# 与程序集兼容性

已检查 VM 4.4 本地组件：

| DLL | Target Framework |
|---|---|
| `VM.Core.dll` | .NET Framework 4.6.1 |
| `VM.PlatformSDKCS.dll` | .NET Framework 4.5 |
| `VMControls.Interface.dll` | .NET Framework 4.5 |
| `MVDCore.Net.dll` 等算法 DLL | .NET Framework 4.0 |

官方全局脚本工程与平台 SDK C# 样例均目标为 .NET Framework 4.6.1；官方全局脚本的 x64 配置明确使用 `PlatformTarget=x64`。生成 C# 时以 .NET Framework 4.6.1/CLR 4/x64 为基线；C# 语言版本仍以 VM 内嵌编译器实测为准。避免 `record`、顶级语句、可空引用类型、范围/索引、async streams、`System.Text.Json`、.NET 5+ API。

`ScriptRefences` 的 `refrencesType` 不得猜测。仅复制同版本成功方案中的引用记录。第三方 DLL 必须确认目标框架、x86/x64、递归依赖和 VM 脚本运行时可见路径。

## 6. Python 第三方库

Python 规则来源于《1.2.68 Python脚本模块：VM4.4Python脚本模块如何使用第三方库》。生成器执行以下固定策略：

1. 仅为 `PyShellModule` 生成 Python，不把 Python 写入 ShellModule 或 GlobalScript。
2. 在脚本开头集中 `import`，并在报告列出标准库与第三方库。
3. 不在脚本执行期间运行 `pip install`、下载依赖或修改系统 Python。
4. 第三方库必须预先部署到 VM Python 模块可搜索的位置；纯 Python 包与含 native DLL/pyd 的包分开验证。
5. native 包必须匹配 VM 使用的 Python 版本、位数和 ABI；不能用系统 Python 可导入来证明 VM 内可导入。
6. 生成后在 VM Python 脚本模块中分别验证 `import`、最小调用、连续执行和异常路径。
7. 未确认 VM Python 解释器路径/版本或依赖部署目录时，输出 `PYTHON_RUNTIME_UNCONFIRMED`，但仍可生成不依赖第三方库的脚本。

## 7. 两套 SDK 的使用边界

### Platform SDK

环境位置：`<VM_ROOT>\Development\V4.x\Samples\C#\PlatformSDKSampleCS`。它面向方案外部的 C# 宿主程序，用于加载方案、控制流程、读取结果。样例 API/程序集不能自动视为 VM 内嵌脚本可用。

### MVD Algorithm SDK

环境位置：`<VM_ROOT>\MVDAlgorithmSDK\Samples\CSharp\BasicSamples`。它面向直接调用算法库。只有相关算法 DLL、依赖与类型在目标脚本运行时可加载，才能用于 C# 用户脚本或外部程序。

生成器必须先判断代码运行位置：VM 内全局脚本、VM 内用户脚本模块、还是 VM 外部宿主程序。用户要求最终 SOL 时，默认前两者，不生成外部 WinForms/WPF 项目。

### 8.1 C# / Python 用户脚本模块

1. 执行 `scripts/materialize_script_base.ps1 -OutputFile <temp.sol>`，把解包模板临时打包为工作 SOL。
2. 根据请求保留 ShellModule、PyShellModule 或两者；用 `deleteModule` 删除不需要的模块。
3. 需要增加同类型脚本时，用 `addModule` 从临时工作 SOL 内的模块复制 RawFrameData。
4. `setBinaryParam` 写 `ShellContent`、`Input`、`Output`、`DynamicInData`、`DynamicOutData`。
5. `addConnection` 建执行顺序，`addBasicSub` 建输入订阅。
6. parse 输出 SOL，检查模块路径、二进制参数、订阅和 warnings。

`setBinaryParam` 改变长度时，内置 CLI 会重建 ModuleFrame；ZIP 使用 VM 兼容回写方式，并同步 UiParamData 变长字段。

### 8.2 全局脚本

先执行 `materialize_script_base.ps1`，再删除两个流程脚本模块，并替换 `SolutionFile\GlobalScript_0` 的完整 JSON（UTF-8 + 末尾 NUL），保持 `VmServer.xml/GlobalScriptInfo` 映射。随后使用内置 CLI parse 校验。

### 8.3 必须验证

```powershell
tools\vm-solution-parser\VMSolutionParser.Cli.exe parse -f output.sol -o output.parse.json
tools\vm-solution-parser\VMSolutionParser.Cli.exe inspect -f output.sol --list
```

最后在目标 VM 4.4 中执行：打开、脚本编译、单次运行、连续运行、输入输出读写、保存、关闭、重新打开。任何一步失败都不得标记为可交付。

## 9. 交付物与错误码

交付：`<name>.sol`、`<name>.contract.json`、`<name>.build-report.md`。

常用阻断码：

| 错误码 | 含义 |
|---|---|
| `VM_HOME_NOT_FOUND` | 环境变量无法定位 VM 根目录 |
| `VM_VERSION_MISMATCH` | 模板、DLL 或目标 VM 版本不一致 |
| `SCRIPT_MODULE_TEMPLATE_MISSING` | 内置解包模板损坏或缺少对应 Shell/PyShell 模块 |
| `SDK_API_UNCONFIRMED` | 接口仅在外部样例或说明中出现，未在脚本运行时验证 |
| `PYTHON_RUNTIME_UNCONFIRMED` | VM Python 版本或解释器路径未确认 |
| `PYTHON_DEPENDENCY_MISSING` | VM 自带 Python 无法发现 Requirement 声明的包 |
| `SOL_REFERENCE_VALIDATION_FAILED` | 写入后的 ShellRefrences 未能从最终 SOL 读回 |
| `SOURCE_OPERATIONS_CONFLICT` | 同一脚本同时声明 source 与非空 operations，会导致语义不唯一 |
| `MODULE_PARAMETER_NOT_FOUND` | `GetModule/SetValue` 的模块或参数不存在 |
| `SOL_PARSE_FAILED` | 回写后无法解析或有严重 warnings |
